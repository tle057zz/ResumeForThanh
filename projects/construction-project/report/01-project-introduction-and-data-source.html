Section 1Project introduction

This project develops a Digital Engineering RFI Analytics & AI Platform using a real construction Request for Information (RFI) dataset from a U.S. Army Corps of Engineers infrastructure project.

The goal is to show how project information stored in spreadsheets and other semi-structured sources can become a structured digital workflow for project reporting, engineering coordination, document control, automation, and AI-assisted analysis.

Project systems before the workbook

A project begins when the team sets it up in Autodesk Forma and establishes the common data environment. Site planning and design come next. An RFI starts only after drawings and specifications are published. The spreadsheet is the export of that controlled register. Two roles inside Forma sit in front of this platform:

  • Common data environment (CDE). Forma Data Management, formerly Autodesk Docs, is the CDE. It is the single place for models, drawings, and specifications. Design files are produced in Revit, Civil 3D, and AutoCAD, then published into the CDE.
  • Electronic document management system (EDMS). Document control is the EDMS function of that same environment. It records the current revision, who approved it, and who it was issued to. Superseded revisions stay in the archive. The site builds from the published issue.

Each file moves through four states in the CDE, following ISO 19650:

  1. Work in progress. Only the authoring team can use the file.
  2. Shared. The file is coordinated and open for review and comment.
  3. Published. The file is the authorised revision.
  4. Archived. A superseded revision is kept as a record.

A contractor then raises an RFI in Forma Build against the published information. The RFI moves from draft, to submitted, to open for review, to answered with one official response, then closed and distributed. The closed RFI can be saved back into the CDE. Submittals, forms, and issues follow the same pattern: each one hangs off the published documents.

The RFI register is exported from that system. The export is the raw Excel workbook. Steps −7 through 0 run from the start of the project to that export. Step 01 is where this platform picks up the register.

Section 2Business context

Construction and infrastructure projects generate large volumes of RFIs throughout design, procurement, and delivery.

RFIs are used when project participants need clarification on issues such as:

  • unclear drawings
  • conflicting specifications
  • missing information
  • constructability questions
  • scope gaps
  • coordination problems
  • compliance questions
  • material or equipment requirements

Because much of this information is stored as free text, it can be difficult to identify recurring engineering issues, document impacts, technical themes, or common clarification categories.

This project turns the RFI register into a structured analytical and AI-enabled platform.

Section 6Original dataset structure

The source workbook contains these main fields:

  • RFI #
  • FROM
  • TASKED
  • DATE RECEIVED
  • QUESTION
  • RESPONSE
  • NOTES
  • Status

RFI #

Identifier assigned to each Request for Information.

FROM

Identifies the organisation or party that submitted the RFI. This field supports counts by submitting organisation, topics by organisation, and the most active submitting parties.

TASKED

Identifies the party or engineering function responsible for reviewing or responding to the RFI.

DATE RECEIVED

The date on which the RFI was received. This supports RFI volume over time, weekly trends, and peak clarification periods.

QUESTION

The original engineering or technical question. This is one of the most valuable fields because it contains unstructured engineering text. Potential derived attributes include discipline, issue type, technical topic, drawing reference, specification reference, equipment reference, and a question summary.

RESPONSE

The official answer or clarification associated with the RFI. This supports question-response analysis, technical resolution analysis, summarisation, and semantic search.

NOTES

Supplementary information that can help identify whether an RFI caused a drawing update, a specification update, an attachment issue, a document revision, or no document change.

Status

The source status where it is populated. The original source status will be preserved. If required, a separate derived status may be created, such as Answered, Open, or Unknown.

The dataset is suitable because it combines a real construction context, structured project fields, unstructured engineering text, genuine RFI questions and responses, and relevant Digital Engineering and document-control use cases.

Section 8Planned transformation

The project will maintain clear lineage between original source data and derived fields.

  2. raw_rfi

  5. SQL and Power BI

Raw layer

The raw layer keeps the ingested record close to the source:

  • rfi_number
  • from_party
  • tasked_to
  • date_received
  • question
  • response
  • notes
  • status_raw
  • source_file
  • ingestion_timestamp

Clean layer

The clean layer standardises RFI identifiers, party names, dates, whitespace, null values, text encoding, status, and duplicates.

Enriched layer

The enriched layer adds derived analytical and AI attributes:

  • discipline
  • issue_type
  • technical_topic
  • reference_type
  • reference_number
  • drawing_update_required
  • spec_update_required
  • document_update_required
  • question_summary
  • response_available
  • classification_confidence

Section 9Data limitations

The source contains approximately 111 RFIs, which is relatively small for supervised machine learning.

It also does not directly contain all fields expected in a mature RFI system, such as due date, response date, closed date, formal priority, cost impact, schedule impact, discipline, issue category, workflow history, and revision history.

Any additional fields derived using rules, manual labelling, or AI will be clearly marked as derived attributes. The project will not present inferred values as if they were present in the original source.

Section 11Project value

The final system demonstrates how a traditional RFI register can be converted into a modern Digital Engineering information platform.

A real USACE RFI workbook is ingested and cleaned using Python, modelled in SQL, visualised through Power BI, and extended in Databricks with NLP classification, document-impact prediction, semantic search, and an AI Copilot for engineering information retrieval.
